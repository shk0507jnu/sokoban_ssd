2. Use Case Diagram

Use Case Diagram — 구현된 기능 범위

구현된 기본 게임의 기능 범위를 보여 준다. 액터 3명(플레이어, 시스템, 레벨 디자이너)과 유스케이스 14개로 이루어지며, 명세서 5.2 목록의 번호·이름과 같다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 플레이어: 게임을 하는 사람. 시작·레벨 선택·이동·밀기·되돌리기·다시 하기·리셋·일시정지·클리어 결과·층 보기(UC-01, 02, 03, 04, 10, 11, 12, 13, 14, 16)와 연결된다.
  • 시스템: 규칙 엔진, 솔버, 저장소처럼 자동으로 동작하는 주체. 입력을 처리하는 UC와 UC-15(기록 저장), UC-17, UC-18에 연결된다.
  • 레벨 디자이너: 레벨 파일·설정 파일을 작성하는 개발자. 도구로 UC-17(검증), UC-18(난이도 곡선), UC-19(설정 조정)을 수행한다.
  • <<extend>>: UC-04(블록 밀기)는 UC-03(평면 이동) 중 목적지에 블록이 있을 때 확장된다.
  • <<include>>: UC-03과 UC-04는 턴이 끝날 때 클리어 판정(UC-14)을 포함하고, UC-14는 기록 저장(UC-15)을 포함하며, UC-17은 난이도 계산(UC-18)을 포함한다.
  • 위쪽 7개(UC-01, 02, 13, 16, 10, 11, 12)는 플레이어 조작 중심, 아래쪽 7개(UC-03, 04, 14, 15, 17, 18, 19)는 규칙·저장·도구 중심이라 두 묶음으로 나눠 배치했다.

대안 · 예외 · 참고

  • 미구현(기믹): UC-05 연쇄 밀기, UC-06 계단, UC-07 리프트, UC-08 포탈, UC-09 중력 낙하. 3D 규칙에서는 중력·바닥이 없어 UC-09, UC-06, UC-07이 필요 없어졌다(README의 "3D 규칙" 참고).
  • UC-03의 "낙하(UC-09) 수행" 단계도 같은 이유로 없다.
관련 코드: 명세서: 2.5D 소코반 요구사항 명세서 5.2 ~ 5.4

3. Class Diagram

CD-01 · 전체 구조 (패키지 단위)

소스 패키지 8개(ui, core, level, solver, config, save, tool, 기본 패키지)와 패키지 사이의 의존 방향을 한 장으로 보여 준다. 클래스 이름만 적은 개요도이고, 세부는 CD-02~05에서 본다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • ui(파랑): Swing 화면 계층. App, Screen, 화면 3종, MenuList, Camera, IsoRenderer, KeyNormalizer, Gfx, Theme. core · level · config · save를 모두 사용한다.
  • core(초록): 순수 게임 규칙. Engine, GameState, Level, Session, Scoring, Direction, TileType, StepResult. Swing에 의존하지 않는다(NFR-1).
  • level(주황): 레벨 파일 파서와 저장소, 난이도 계산. core의 Level을 만들고, config의 가중치를 쓴다.
  • solver · tool(보라): Solver는 Engine을 그대로 재사용해 BFS로 풀고, LevelTool은 level · solver · config를 묶어 검증 도구로 쓴다.
  • config(노랑) · save(회색): 설정 파일과 기록 파일 처리. save는 다른 패키지에 의존하지 않는다.
  • core → config: Session이 점수 계산 때 GameConfig(κ, 별 비율)를 읽기 때문에 core에서 config로 가는 화살표가 하나 있다(아래쪽 우회선).
  • 기본 패키지 sokoban: Main 하나뿐. ui의 App을 만들어 실행한다.
관련 코드: src/sokoban/** (패키지 구조), README.md "구조"

CD-02 · core — 게임 규칙 · 상태

게임 규칙의 핵심. 레벨 정의(Level), 불변 상태(GameState), 규칙 함수(Engine), 한 번의 입력 결과(StepResult), 플레이 세션(Session)과 점수 계산(Scoring)의 구조를 보여 준다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • Direction: 3차원 6방향 열거형(UP, RIGHT, DOWN, LEFT, ABOVE, BELOW). 각 값이 풀이 기호(U R D L T B)와 이동량(dx, dy, dz)을 가진다. 화면에서 x+ = 오른쪽 아래, y+ = 왼쪽 아래, z+ = 위다.
  • TileType: 정적 셀 4종(EMPTY, WALL, HOLE, GOAL). 블록과 플레이어는 셀이 아니라 GameState가 가진다.
  • Level: 불변 레벨 정의. 격자 W×D×H를 1차원 배열 하나로 저장하고 idx(x, y, z) = (z·d + y)·w + x 로 인덱스를 만든다. neighbor(idx, dir)는 격자 밖이면 -1(격자 밖은 고체)을 돌려준다. initial(GameState)을 합성으로 가진다.
  • GameState: 불변 상태. 플레이어 위치, 정렬된 블록 배열, 정렬된 남은 구멍 배열. withPlayer / withPush / withFill 이 새 객체를 만든다. equals/hashCode가 있어 되돌리기 스냅샷과 솔버의 중복 상태 제거에 같이 쓴다(NFR-3).
  • Engine: 상태를 바꾸지 않는 순수 함수 모음. step(lv, s, dir)는 StepResult를 만들고, 막히면 null을 돌려준다(이동 횟수에 포함하지 않음, FR-1.4). isCleared는 모든 목표에 블록이 있는지 본다.
  • StepResult: 유효한 입력 1회의 결과(처리 후 상태, 방향, 플레이어·블록 이전/이후 위치, 블록 소멸 여부, 클리어 여부). 렌더러가 애니메이션을 그릴 때도 쓴다.
  • Session: 한 레벨의 플레이. 현재 상태, undoStack · redoStack(스냅샷 스택), undoCount, cleared. moves() = undoStack 크기. score() / stars()는 Scoring과 설정(GameConfig)으로 계산한다.
  • Scoring: 점수 = max(0, round(1000 × min(1, 최적/이동)) − κ × 되돌리기 횟수). 별은 이동 ≤ ⌈최적 × r3⌉이면 3개, ≤ ⌈최적 × r2⌉이면 2개, 그 외는 1개.
  • 회색 상자 GameConfig는 config 패키지 클래스를 참조만 한 것이다(CD-03).

대안 · 예외 · 참고

  • 점선 화살표 = 사용(<<use>>)·생성(<<create>>), 속이 빈 마름모 = 집약(Session이 여러 GameState를 스택으로 보관), 채운 마름모 = 합성(Level이 initial을 소유).
  • 밑줄이 있는 메서드는 static이다(Engine의 모든 메서드, GameState.of 등).
관련 코드: core/Direction.java, TileType.java, Level.java, GameState.java, Engine.java, StepResult.java, Session.java, Scoring.java

CD-03 · level · config — 레벨 로드 · 난이도 · 설정

레벨 파일을 읽어 Level 목록을 만들고 난이도 순으로 정렬하는 흐름과, 설정 파일을 읽는 GameConfig의 구조를 보여 준다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • LevelParser.parse(source, lines): 레벨 텍스트를 Level로 바꾼다. 메타데이터(id, name, optimalMoves, solution, star3, star2)와 layer N 격자를 읽고, 알 수 없는 문자·플레이어 중복·목표 없음·블록 부족(블록 수 < 목표 + 구멍) 같은 오류를 검사한다.
  • LevelFormatException: 어느 파일의 몇 번째 줄이 문제인지(source, line)를 담는다(NFR-8). parse가 던진다.
  • LevelRepository.load(dir, cfg): 폴더의 *.txt를 읽어 Level 목록을 만든다. 오류가 있는 레벨은 목록에서 제외하고 errors에 메시지를 모은다. optimalMoves가 없거나 id가 중복이어도 제외한다. 마지막에 난이도 D 오름차순(같으면 파일 이름 순)으로 정렬한다.
  • Difficulty.score(lv, cfg): D = Σ(가중치 × 기믹 수) + α·최적 이동 + β·블록 수 + γ·(기믹 종류 − 1) + δ·(사용 층 수 − 1). 기본 게임은 기믹이 없어 기믹 항이 0이다.
  • GameConfig: κ(되돌리기 페널티), 별 비율(star3Ratio, star2Ratio), 난이도 계수(α β γ δ), 급등 한계(maxDeltaD), 기믹 가중치, maxChain을 담는다. 값이 범위 밖이거나 형식이 틀리면 기본값으로 대체하고 warnings에 경고를 남긴다. defaults()는 파일 없이 기본값만 쓴다(테스트용).
  • 회색 상자 Level은 core 패키지 클래스를 참조만 한 것이다(CD-02).

대안 · 예외 · 참고

  • LevelParser는 상태가 없는 static 유틸리티, LevelRepository는 load로만 만들 수 있는 읽기 전용 결과 객체(생성자가 private)다.
관련 코드: level/LevelParser.java, LevelFormatException.java, LevelRepository.java, Difficulty.java, config/GameConfig.java, config/game.properties

CD-04 · solver · tool · save — 솔버 · 검증 도구 · 기록 저장

레벨 디자이너용 검증 도구(LevelTool)와 BFS 솔버(Solver), 플레이어 기록 저장소(SaveStore)의 구조를 보여 준다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • LevelTool: main(args)로 실행하는 도구. 폴더의 레벨을 파싱하고 Solver로 풀어 optimalMoves와 풀이 경로를 파일에 기록한다. --check 옵션이면 파일은 고치지 않고 기록값이 솔버 결과와 같은지만 확인한다. rewrite()가 메타데이터 줄을 갱신한다. 마지막에 난이도 곡선을 검사한다.
  • Solver.solve(lv, maxStates, timeLimitMillis): Engine.step을 그대로 재사용하는 BFS. GameState의 equals/hashCode로 중복 상태를 건너뛰므로 처음 찾은 해가 최소 이동이다. 탐색 한도는 LevelTool에서 상태 3,000,000개, 60초다.
  • Solver.Result: 상태(Status), 이동 횟수, 풀이 경로, 탐색한 상태 수, 걸린 시간. Solver.Status는 SOLVED / UNSOLVABLE / LIMIT_EXCEEDED. Solver.Node는 큐에 넣는 내부 노드(상태, 부모, 방향, 깊이)로 풀이 경로를 거슬러 올라가 복원한다.
  • SaveStore: 레벨별 최고 점수 · 최다 별 · 최소 이동 횟수를 저장한다. update()는 하나라도 갱신되면 true(신기록)를 돌려준다. 파일이 없거나 손상되면 빈 기록으로 시작하고 loadWarning을 남긴다. 저장 파일은 ~/.sokoban25d/save.properties(-Dsokoban.save로 변경).
  • SaveStore.save(): 임시 파일에 쓴 뒤 교체한다(원자적 이동, 지원하지 않으면 일반 교체). 실패하면 IOException을 던지고, 호출한 PlayScreen이 게임을 막지 않고 알림만 띄운다.
  • 위쪽 회색 상자 LevelParser · Difficulty · GameConfig · Engine은 다른 패키지 클래스를 참조만 한 것이다.

대안 · 예외 · 참고

  • SaveStore는 ui 패키지(App이 보유하고 PlayScreen이 클리어 시 갱신)가 사용한다. 연결선은 CD-05에 있다.
관련 코드: tool/LevelTool.java, solver/Solver.java, save/SaveStore.java

CD-05 · ui — 화면 · 카메라 · 렌더러

화면 계층(Swing). App이 화면 하나를 들고 있고, 세 화면이 Screen 인터페이스를 구현하며, PlayScreen이 카메라와 렌더러를 사용하는 구조를 보여 준다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • App: 애플리케이션 루트. 창(JFrame)과 입력 패널을 갖고, 설정 · 레벨 목록 · 기록(GameConfig, LevelRepository, SaveStore)을 공용 데이터로 보유한다. showMainMenu / showLevelSelect / startLevel로 화면을 만들어 바꾼다. isUnlocked(index)는 첫 레벨이거나 이전 레벨을 별 1개 이상으로 클리어했을 때 true다. notify(msg)는 5초 동안 안내 문구를 띄운다. 15ms 타이머로 tick과 repaint를 돌린다.
  • Screen: 화면 인터페이스. paint와 입력(키, 마우스) 메서드를 정의하고 대부분 기본 구현(빈 메서드)이 있다. 모든 호출은 EDT에서 일어난다(NFR-5).
  • MainMenuScreen: 시작 / 종료 메뉴와 클리어 수 표시. LevelSelectScreen: 난이도 순 카드 목록, 해금·별·최고 기록 표시, 잠긴 레벨 선택 시 안내. PlayScreen: 실제 플레이.
  • PlayScreen: Session, IsoRenderer, Camera를 합성으로 갖는다. 모드는 PLAYING / PAUSED / CLEARED. 이동 애니메이션(110ms) 중의 입력은 마지막 하나만 pending으로 큐잉한다. 클리어하면 onCleared()가 점수·별을 계산하고 SaveStore를 갱신한다.
  • MenuList: 세로 메뉴(키보드와 마우스 모두 지원). 메인 메뉴 1개, PlayScreen에서 일시정지 메뉴와 클리어 메뉴 2개를 쓴다.
  • Camera: 수직축 회전(yaw)과 기울기(pitch). 키로는 90° 단위, 마우스 드래그로는 자유 회전 후 놓으면 90°로 정렬된다. mapKey()가 화면 기준 키 방향을 현재 시점의 격자 방향으로 바꾼다(카메라를 돌려도 ↑는 화면 오른쪽 위).
  • IsoRenderer: 3차원 격자를 아이소메트릭으로 그린다(화가 알고리즘, 면 법선으로 뒷면 제거). 진행 중 애니메이션은 Anim(step, t) 레코드로 받는다. layerFocus가 켜지면 플레이어 층 위를 흐리게 그린다.
  • KeyNormalizer: 한글 입력기가 켜져 있어도 단축키(Z, Y, R, V, WASD 등)가 동작하도록 두벌식 자모를 물리 키로 되돌린다. Gfx(문자열 정렬, 별 그리기)와 Theme(색, 글꼴)은 모든 화면이 쓰는 유틸리티다.

대안 · 예외 · 참고

  • 각 화면은 App 참조(app 필드)를 갖지만 선이 겹쳐 그리지 않았다. 세 화면이 App · Gfx · Theme을 사용한다.
  • 회색 상자 GameConfig · LevelRepository · SaveStore · Session은 다른 패키지 클래스를 참조만 한 것이다.
관련 코드: ui/App.java, Screen.java, MainMenuScreen.java, LevelSelectScreen.java, PlayScreen.java, MenuList.java, Camera.java, IsoRenderer.java, KeyNormalizer.java, Gfx.java, Theme.java

4. Sequence Diagram (기본 흐름)

SD-01 · UC-01 — 게임 시작 및 기록 불러오기

앱을 실행하면 설정 · 레벨 목록 · 기록을 읽고 메인 메뉴를 보여 준다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 객체 App은 Main이 만들고, GameConfig · LevelRepository · LevelParser · Difficulty는 static 호출이라 밑줄 없는 클래스로 그렸다.
  • 읽는 순서가 명세 그대로다: 설정 → 레벨 목록 → 기록.
  • 레벨은 LevelRepository.load 안에서 파일마다 parse를 반복(5번 메시지)하고, 레벨마다 난이도를 계산(6번)해 D 오름차순으로 정렬한다.

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 앱을 실행한다 → Main.main(args).
  2. Main이 App(home)을 만든다 (home = -Dsokoban.home, 기본 ".").
  3. App 생성자가 GameConfig.load(home/config/game.properties)로 설정을 읽는다.
  4. LevelRepository.load(home/levels, config)로 레벨 목록을 만든다.
  5. (반복) 레벨 파일마다 LevelParser.parse(name, lines).
  6. (반복) 레벨마다 Difficulty.score(lv, cfg)로 난이도를 계산한다.
  7. SaveStore(defaultFile())를 만든다 — 생성자가 저장 파일을 읽는다.
  8. Main이 App.start()를 호출한다.
  9. App이 showMainMenu()를 호출한다.
  10. MainMenuScreen을 만들어 표시한다.

대안 · 예외 · 참고

  • 1a 레벨 파일 오류: 해당 레벨 ID와 오류 위치를 LevelRepository.errors에 모으고 그 레벨은 목록에서 제외한다. 시작할 때 notify로 "레벨 파일 오류 N건"을 알린다.
  • 2a 저장 파일 없음·손상: 빈 기록(1번 레벨만 해금)으로 시작하고 loadWarning을 알린다.
관련 코드: Main.java, ui/App.java, config/GameConfig.java, level/LevelRepository.java, level/LevelParser.java, level/Difficulty.java, save/SaveStore.java

SD-02 · UC-02 — 레벨 선택

메인 메뉴에서 "시작"을 고르면 레벨 목록이 뜨고, 해금된 레벨을 고르면 플레이 화면과 세션이 만들어진다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • "시작"을 누르면 처음 열어야 할 레벨(firstOpenLevel: 해금됐지만 아직 클리어하지 않은 첫 레벨)에 포커스를 맞춰 레벨 선택 화면을 연다.
  • 해금 판정은 App.isUnlocked(i) → SaveStore.cleared(이전 레벨 id)로, 이전 레벨을 별 1개 이상으로 클리어해야 true다(FR-5.7).
  • LevelSelectScreen, PlayScreen, Session은 흐름 중간에 생성되므로 박스를 생성 시점 높이에 그렸다.

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 "시작"을 선택한다 (Enter / 클릭).
  2. MainMenuScreen이 App.firstOpenLevel()로 포커스할 레벨을 구한다.
  3. (내부) firstOpenLevel이 SaveStore.cleared(levelId)를 확인한다.
  4. App.showLevelSelect(focus) 호출.
  5. LevelSelectScreen(app, focus)이 만들어진다.
  6. 사용자가 해금된 레벨을 선택한다 (Enter / 클릭).
  7. LevelSelectScreen이 App.isUnlocked(i)로 해금 여부를 묻는다.
  8. (내부) SaveStore.cleared(이전 레벨 id).
  9. 해금이면 App.startLevel(i)를 호출한다.
  10. PlayScreen(app, i)이 만들어진다.
  11. PlayScreen 생성자가 Session(level, config)을 만든다.

대안 · 예외 · 참고

  • 2a 잠긴 레벨을 선택하면 isUnlocked가 false라서 안내 문구("잠긴 레벨이다. 이전 레벨을 별 1개 이상으로 클리어하세요.")만 표시하고 진입하지 않는다.
  • 불러온 레벨이 하나도 없으면 "시작" 자체가 notify("불러온 레벨이 없다")만 띄운다.
관련 코드: ui/MainMenuScreen.java, ui/LevelSelectScreen.java, ui/App.java, ui/PlayScreen.java, core/Session.java

SD-03 · UC-03 — 평면 이동

플레이어가 방향키로 빈 칸으로 이동한다. 3D 규칙이라 방향은 평면 4방향 + 위(Q/Space/PageUp) · 아래(E/Shift/PageDown) 6방향이다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 세로 막대가 많아 보이지만 한 입력 처리 경로는 PlayScreen → Camera → Session → Engine → (Level, GameState)로 단순하게 내려간다.
  • Engine.step은 상태를 바꾸지 않는다. 새 GameState와 이동 정보(StepResult)만 만들어 Session에 돌려주고, Session이 스냅샷을 쌓은 뒤 현재 상태를 교체한다.
  • 입력은 항상 화면 기준이라 Camera.mapKey가 현재 시점의 격자 방향으로 바꿔 준다.
  • 이동 애니메이션(110ms) 중에 들어온 입력은 PlayScreen이 마지막 하나만 pending으로 두었다가 애니메이션이 끝나면 처리한다(그림에는 생략).

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 방향키 / WASD / Q / E를 누른다 → PlayScreen.keyPressed(e).
  2. Camera.mapKey(key)로 화면 방향을 격자 방향 d로 바꾼다 (위/아래 키는 그대로).
  3. Session.move(d)를 호출한다.
  4. Session이 Engine.step(level, state, d)를 호출한다.
  5. Engine이 Level.neighbor(from, dir)로 목적지 칸을 구한다.
  6. 목적지가 빈 칸(EMPTY, GOAL, 메워진 구멍)이면 GameState.withPlayer(to)로 새 상태를 만든다.
  7. Engine.isCleared(lv, next)로 클리어 여부를 계산해 StepResult에 담는다.
  8. Session이 이전 상태를 undoStack에 쌓고(redoStack 비움) state를 갱신한다 → 이동 횟수 +1.
  9. PlayScreen이 animStep = r 로 두고 이동 애니메이션을 시작한다.

대안 · 예외 · 참고

  • 3a 목적지에 블록이 있으면 블록 밀기로 넘어간다 → SD-04.
  • 3d 벽, 구멍(메워지지 않은), 격자 밖이면 step()이 null을 돌려준다 → 상태와 이동 횟수 모두 불변.
  • 명세 3단계의 "낙하(UC-09)"는 중력이 없는 3D 규칙이라 구현하지 않았다.
관련 코드: ui/PlayScreen.java (keyPressed, move), ui/Camera.java (mapKey), core/Session.java (move), core/Engine.java (step), core/Level.java (neighbor), core/GameState.java (withPlayer)

SD-04 · UC-04 — 블록 밀기

블록 쪽으로 이동 입력을 하면 블록과 플레이어가 같은 방향으로 한 칸씩 움직인다. 블록이 구멍에 들어가면 블록과 구멍이 함께 사라진다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 세로 막대가 많아 보이지만 한 입력 처리 경로는 PlayScreen → Camera → Session → Engine → (Level, GameState)로 단순하게 내려간다.
  • Engine.step은 상태를 바꾸지 않는다. 새 GameState와 이동 정보(StepResult)만 만들어 Session에 돌려주고, Session이 스냅샷을 쌓은 뒤 현재 상태를 교체한다.
  • 입력은 항상 화면 기준이라 Camera.mapKey가 현재 시점의 격자 방향으로 바꿔 준다.
  • 이동 애니메이션(110ms) 중에 들어온 입력은 PlayScreen이 마지막 하나만 pending으로 두었다가 애니메이션이 끝나면 처리한다(그림에는 생략).
  • 한 번에 블록 1개만 민다. 뒤 칸에 벽 · 다른 블록 · 격자 밖이 있으면 막힌다(연쇄 없음).
  • 10번과 11번은 조건 분기다: 뒤 칸이 메워지지 않은 구멍이면 withFill(블록 소멸 + 구멍 제거), 아니면 withPush(블록 이동). 둘 다 플레이어도 함께 이동한다.

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 블록 방향으로 입력한다 → PlayScreen.keyPressed(e).
  2. Camera.mapKey(key)로 격자 방향 d를 구한다.
  3. Session.move(d).
  4. Engine.step(level, state, d).
  5. Level.neighbor(from, dir)로 목적지 to를 구한다.
  6. GameState.hasBlock(to)로 목적지에 블록이 있는지 확인한다.
  7. Level.neighbor(to, dir)로 블록 뒤 칸 behind를 구한다.
  8. GameState.hasBlock(behind)로 뒤 칸이 다른 블록인지 확인한다.
  9. Level.tile(behind)로 뒤 칸 종류를 확인한다 (WALL이면 막힘).
  10. [HOLE] withFill(to, to, behind): 블록 소멸 + 구멍 소멸.
  11. [그 외] withPush(to, to, behind): 블록을 behind로 이동.
  12. Engine.isCleared(lv, next).
  13. Session이 스냅샷을 쌓고 상태를 갱신한다 (이동 횟수 +1).
  14. PlayScreen이 블록 이동 · 소멸 애니메이션을 시작한다.

대안 · 예외 · 참고

  • 2a 뒤 칸이 벽, 다른 블록, 격자 밖이면 step()이 null을 돌려준다 → 상태와 이동 횟수 불변.
  • 명세의 "방향 제한", "포탈 칸 진입", "연쇄 밀기(UC-05)"는 기믹이라 구현하지 않았다.
관련 코드: core/Engine.java (step), core/GameState.java (hasBlock, withPush, withFill), core/Level.java (neighbor, tile), core/Session.java (move)

SD-05 · UC-10 — 되돌리기

직전 입력 이전 상태로 돌아간다. 이동 횟수는 1 줄고 되돌리기 횟수는 1 는다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • Session이 불변 GameState 스냅샷 스택을 쓰므로 되돌리기는 스택 pop과 state 교체만으로 끝난다(FR-3.7).
  • 되돌리기 횟수(undoCount)는 점수의 κ 페널티에 반영된다. 이동 횟수 moves()는 undoStack의 크기다.
  • 되돌리기 직전에 finishAnim()으로 진행 중인 애니메이션을 끝내고 대기 입력을 비운다.

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 Z를 누른다 → PlayScreen.keyPressed(e).
  2. PlayScreen.finishAnim()으로 애니메이션을 끝낸다.
  3. Session.undo()를 호출한다.
  4. (내부) redoStack.push(state), state = undoStack.pop(), undoCount++.
  5. HUD가 moves()와 undoCount()를 읽어 갱신한다.

대안 · 예외 · 참고

  • 1a undoStack이 비었거나 이미 클리어했으면 undo()가 false를 돌려주고 아무 일도 일어나지 않는다.
관련 코드: ui/PlayScreen.java (playKey), core/Session.java (undo, moves, undoCount)

SD-06 · UC-11 — 다시 하기

되돌렸던 입력을 다시 적용한다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 되돌릴 때 redoStack에 쌓아 둔 상태를 꺼내 적용한다. 이동 횟수가 다시 1 늘어난다(되돌리기 횟수는 그대로).
  • 되돌린 뒤 새 유효 이동(Session.move)이 생기면 redoStack은 비워진다(Session.move의 redoStack.clear()).

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 Y를 누른다 → PlayScreen.keyPressed(e).
  2. PlayScreen.finishAnim().
  3. Session.redo()를 호출한다.
  4. (내부) undoStack.push(state), state = redoStack.pop().
  5. HUD가 moves()를 읽어 갱신한다.

대안 · 예외 · 참고

  • 1a redoStack이 비었거나 클리어 상태이면 redo()가 false를 돌려주고 아무 일도 일어나지 않는다.
관련 코드: ui/PlayScreen.java (playKey), core/Session.java (redo, move)

SD-07 · UC-12 — 레벨 리셋

레벨을 처음 상태로 되돌린다. 이동 횟수와 되돌리기 횟수가 0이 된다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 이동 횟수가 0이 아니면 확인 대화상자(JOptionPane)를 띄운다. 이동이 없으면 바로 초기화한다.
  • 일시정지 메뉴의 "다시 시작"도 같은 PlayScreen.reset()을 쓴다(SD-08).
  • 리셋은 되돌릴 수 없다. Session.reset()이 state를 level.initial로 두고 두 스택과 undoCount, cleared를 모두 초기화한다.

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 R을 누른다 → PlayScreen.keyPressed(e).
  2. PlayScreen.finishAnim().
  3. Session.moves()로 이동 횟수를 확인한다.
  4. [이동 횟수 != 0] JOptionPane.showConfirmDialog(...)로 확인을 묻는다.
  5. 사용자가 확인을 선택한다.
  6. [확인 또는 이동 0회] Session.reset().

대안 · 예외 · 참고

  • 2a 취소를 누르면 상태를 그대로 유지한다.
  • 리셋 중 Reset 되돌리기는 명세 FR-3.5의 검토 항목이라 지원하지 않는다(횟수 0으로 초기화).
관련 코드: ui/PlayScreen.java (reset), core/Session.java (reset)

SD-08 · UC-13 — 일시정지 및 메뉴 조작

Esc로 일시정지 메뉴(계속, 다시 시작, 레벨 선택, 메인 메뉴)를 열고 항목을 고른다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • PlayScreen의 mode가 PLAYING → PAUSED로 바뀌면 이동 입력은 무시되고 메뉴 입력만 받는다.
  • 메뉴 항목 번호 i는 MenuList.key(e)가 돌려주고(선택 확정 전에는 -1), PlayScreen.pauseAction(i)이 처리한다.
  • 메뉴 항목: 0 계속 / 1 다시 시작 / 2 레벨 선택 / 3 메인 메뉴.

메시지 흐름 (그림의 번호 순서)

  1. 사용자가 Esc를 누른다 → PlayScreen.keyPressed(e).
  2. finishAnim()으로 애니메이션을 끝내고 mode = PAUSED.
  3. 사용자가 방향키 / Enter를 누른다.
  4. MenuList.key(e)가 선택된 항목 번호 i를 돌려준다.
  5. PlayScreen.pauseAction(i)가 항목을 처리한다.
  6. [i == 2] App.showLevelSelect(levelIndex).
  7. [i == 3] App.showMainMenu().

대안 · 예외 · 참고

  • i == 0 계속: mode = PLAYING. i == 1 다시 시작: mode = PLAYING 후 reset() — SD-07.
  • 일시정지 중 Esc를 한 번 더 누르면 계속(mode = PLAYING)한다.
관련 코드: ui/PlayScreen.java (keyPressed, pauseAction), ui/MenuList.java (key), ui/App.java

SD-09 · UC-14 · UC-15 — 레벨 클리어 · 결과 확인 · 기록 저장

마지막 이동 애니메이션이 끝나면 점수와 별을 계산하고, 기록을 갱신 · 저장한 뒤 결과 메뉴를 보여 준다. UC-14(클리어 및 결과 확인)와 UC-15(기록 저장)를 한 장에 합쳤다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 클리어 판정은 이동 직후 Engine이 하지만(SD-03, 04의 isCleared) 결과 처리는 애니메이션이 끝난 tick에서 시작한다(첫 메시지).
  • 점수 = max(0, round(1000 × min(1, 최적/이동)) − κ × 되돌리기 횟수). 별은 설정의 ★★★ / ★★ 비율(레벨별 덮어쓰기 가능)로 정한다.
  • SaveStore.update는 최고 점수 · 최다 별 · 최소 이동 횟수를 각각 갱신될 때만 덮어쓰고, 하나라도 바뀌면 true(신기록)를 돌려준다.
  • UC-15: 신기록일 때만 save()를 호출한다. 임시 파일에 쓴 뒤 교체한다.
  • 다음 레벨이 있으면 메뉴는 "다음 레벨 / 다시 도전 / 레벨 선택", 마지막 레벨이면 "다시 도전 / 레벨 선택"이다.

메시지 흐름 (그림의 번호 순서)

  1. (tick) 애니메이션이 끝나면 Session.isCleared()를 확인한다.
  2. PlayScreen.onCleared()가 시작된다 (mode = CLEARED).
  3. resScore = Session.score().
  4. Session이 Scoring.score(optimal, moves, undoCount, kappa)를 호출한다.
  5. resStars = Session.stars().
  6. Session이 Scoring.stars(optimal, moves, r3, r2)를 호출한다.
  7. newRecord = SaveStore.update(level.id, resScore, resStars, moves).
  8. [newRecord] SaveStore.save() — UC-15 기록 저장.
  9. [IOException] App.notify(msg)로 저장 실패를 알린다(게임은 계속).
  10. MenuList("다음 레벨", "다시 도전", "레벨 선택")을 만든다.
  11. 사용자가 항목을 선택한다 → PlayScreen.keyPressed(e).
  12. clearAction(i)가 App.startLevel(levelIndex + 1) 등을 호출한다.

대안 · 예외 · 참고

  • 2a 신기록이 아니면 기존 기록을 유지한다(save도 호출하지 않는다). 신기록이면 "신기록!"을 강조해 표시한다.
  • 5a 마지막 레벨이면 "다음 레벨" 대신 완주 메시지를 보여 준다.
  • UC-15 2a 저장에 실패해도 게임 진행은 막지 않고 오류 알림만 표시한다.
관련 코드: ui/PlayScreen.java (tick, onCleared, clearAction), core/Session.java (score, stars), core/Scoring.java, save/SaveStore.java (update, save)

SD-11 · UC-17 — 레벨 검증 및 최적해 산출

레벨 디자이너가 LevelTool을 실행하면 레벨 파일을 검사하고 BFS 솔버로 풀어 최적 이동 횟수와 풀이 경로를 파일에 기록한다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • Solver는 게임과 같은 Engine.step을 그대로 쓴다(NFR-1). BFS라 처음 찾은 해가 최소 이동이다.
  • 결과는 레벨 파일의 optimalMoves / solution 줄로 기록된다. --check 옵션이면 파일은 고치지 않고 기록값과 솔버 결과가 같은지만 비교한다.
  • optimalMoves가 없는 레벨은 게임에서 로드되지 않으므로(LevelRepository), 이 도구가 "출고" 관문이다.
  • 난이도 D 계산(7번)은 UC-18과 겹친다 — SD-12.

메시지 흐름 (그림의 번호 순서)

  1. 디자이너가 LevelTool을 실행한다 → main(args).
  2. GameConfig.load(config/game.properties).
  3. LevelParser.parse(name, lines)로 파일을 검사한다.
  4. Solver.solve(lv, maxStates, timeLimit).
  5. (반복) BFS 탐색: Engine.step(lv, state, dir)을 6방향으로 호출한다.
  6. Level.withSolution(r.moves(), r.path())로 풀이가 기록된 Level을 만든다.
  7. Difficulty.score(solved, cfg)로 난이도를 계산한다 (UC-18).
  8. rewrite(lines, moves, path)로 파일의 optimalMoves / solution 줄을 갱신한다.

대안 · 예외 · 참고

  • 2a 형식 오류: "[형식 오류] 파일:줄 …" 출력, 실패로 집계.
  • 3a 해 없음(UNSOLVABLE): "[풀이 불가]" 출력, 출고 불가.
  • 3b 상태 수 / 시간 한도 초과(LIMIT_EXCEEDED): "[검증 불가]" 출력, 출고 불가.
  • 실패가 하나라도 있으면 종료 코드 1로 끝난다.
관련 코드: tool/LevelTool.java, solver/Solver.java, level/LevelParser.java, core/Level.java (withSolution), level/Difficulty.java

SD-12 · UC-18 — 난이도 점수 산출 및 곡선 검증

레벨마다 난이도 D를 계산하고, 레벨 순서대로 D가 줄어들거나 너무 급하게 오르는 구간을 찾아 경고한다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • D = Σ(가중치 × 기믹 수) + α·최적 이동 + β·블록 수 + γ·(기믹 종류 − 1) + δ·(사용 층 수 − 1). 계수는 설정 파일에서 온다.
  • 곡선 검사는 파일 이름 순서(디자이너가 의도한 순서)를 기준으로, 앞 레벨과의 차이 delta = D[i] − D[i−1]를 본다.
  • 게임에서는 LevelRepository.load가 같은 Difficulty.score로 레벨 목록을 D 오름차순으로 정렬한다(그림에는 생략).

메시지 흐름 (그림의 번호 순서)

  1. 디자이너가 LevelTool을 실행한다.
  2. (반복) 레벨마다 Difficulty.score(solved, cfg)로 D를 구해 목록에 기록한다.
  3. (반복) i = 1 … n−1 에 대해 delta = ds[i] − ds[i−1]을 계산한다.
  4. [delta < 0 또는 delta > maxDeltaD] "[곡선 경고] 이전 → 현재 : D 감소 / D 급등"을 출력한다.

대안 · 예외 · 참고

  • 경고는 실패로 집계되지 않는다(출력만 한다). 검증 실패(풀이 불가 등)만 종료 코드에 반영된다.
관련 코드: tool/LevelTool.java (main), level/Difficulty.java, config/GameConfig.java (maxDeltaD)

SD-13 · UC-19 — 설정 값 조정

디자이너가 설정 파일의 값(κ, 별 비율, 난이도 계수 등)을 고치면 다음 실행 때 읽어 적용한다.

이미지를 클릭하면 원본 PNG가 열린다

핵심 · 읽는 법

  • 설정은 코드에 하드코딩하지 않고 config/game.properties에서 읽는다(FR-5.4). 게임(App)과 LevelTool 모두 같은 GameConfig.load를 쓴다.
  • GameConfig의 intOf / doubleOf가 키마다 범위를 검사한다(예: kappa 0~100000, star3Ratio 1.0 이상). 문제가 있으면 기본값을 쓰고 경고 메시지를 warnings에 모은다.
  • star2Ratio가 star3Ratio보다 작으면 "별 기준이 뒤집혀 있다"는 경고도 남긴다.

메시지 흐름 (그림의 번호 순서)

  1. 디자이너가 설정 파일을 수정한 뒤 게임 또는 LevelTool을 실행한다.
  2. GameConfig.load(file)로 설정을 읽는다.
  3. (내부) 키마다 intOf(...) / doubleOf(...)로 값을 읽고 검사한다.
  4. [값 오류] warnings.add(...)로 경고를 남기고 기본값을 쓴다.
  5. App이 config.warnings를 "[설정 경고]"로 콘솔에 출력한다.

대안 · 예외 · 참고

  • 2a 값이 범위 밖이거나 형식이 틀리면 기본값으로 대체하고 경고를 남긴다. 설정 파일이 아예 없거나 읽을 수 없어도 모든 값을 기본값으로 쓴다.
관련 코드: config/GameConfig.java (load, intOf, doubleOf), config/game.properties, ui/App.java
